This page traces one specific issue end-to-end, across every file involved, because each individual file looks reasonable on its own - the mismatch only becomes visible by reading `schemas.py`, `predict.py`, and the committed model artifacts together.

## The evidence trail for `road_type`

| File | What it says about `road_type` |
| --- | --- |
| `app/schemas.py` | `road_type` is a required `Literal['highway', 'hill', 'city', 'terai']` field, added with the comment `# CRITICAL ADDITION FOR NEPAL DATA` - no default value |
| `app/main.py` | A comment directly next to `input_data = request.dict()` reads: "We now include `road_type` in the input_data for better Nepal accuracy" |
| `data/sample_data.csv` | Has a `road_type` column, with real Nepal route data generated by `generate_nepal_data.py` (`highway`/`hill`/`city`/`terai`, matching the schema's four values exactly) |
| `app/ml/train.py` | `feature_columns` is a fixed list of 6 names; `road_type` is not among them and is never referenced anywhere in the file |
| `models/feature_names.pkl` (inspected directly) | Contains exactly `distance_km`, `traffic_hours`, `vehicle_avg_speed`, `vehicle_type_encoded`, `road_condition_encoded`, `weather_condition_encoded` - confirmed, no `road_type` |
| `app/ml/predict.py` | `preprocess_input`'s `feature_dict` has exactly those same 6 keys; `road_type` from the input is read into `processed` but never copied into `feature_dict` |

So: the training data has the column, the API requires the field and describes it as important for accuracy, but the code that actually turns data into a trained model - and the code that turns a request into a prediction - both skip it entirely. Every `/predict` response today is computed identically for a highway trip and a hill trip of the same distance/speed/conditions, despite `road_type`'s own schema description stating hill roads are "significantly slower." This most likely happened because `schemas.py` (and the training CSV) were updated with Nepal-specific fields in a later pass, while `train.py`/`predict.py` were never updated to match - `feature_columns` in `train.py` looks exactly like an earlier, pre-Nepal version of the feature list that just never got a `road_type` entry added.

## Two more values the schema accepts that the model can't handle

`models/label_encoders.pkl` (inspected directly) shows the actual trained categories are narrower than what `schemas.py` allows:

| Field | `schemas.py` allows | The trained `LabelEncoder`'s known classes |
| --- | --- | --- |
| `vehicle_type` | car, truck, motorcycle, suv, van, microbus, bus, jeep, scooter (9 values) | bus, car, jeep, microbus, motorcycle, scooter, truck (7 values - no suv, no van) |
| `weather_condition` | clear, rain, fog, snow, cloudy, dust (6 values) | clear, cloudy, dust, fog, rain (5 values - no snow) |

A request with `vehicle_type: "suv"`, `vehicle_type: "van"`, or `weather_condition: "snow"` passes Pydantic validation (all three are valid per the schema's `Literal` types) but then fails inside `preprocess_input`, where `LabelEncoder.transform` raises a `ValueError` for a category the encoder never saw during training - caught by `main.py`'s broad exception handler and returned as a `500`, as described in `02-prediction-pipeline.mdx`.

## Where the two different category lists came from

The two vehicle-type/weather-condition lists trace back to the project's two separate synthetic-data generators (see `04-model-training-and-data.mdx`):

- **`generate_data.py`** (the generic, non-Nepal generator) uses vehicle types car/truck/motorcycle/suv/van and weather conditions clear/rain/fog/snow/cloudy - this matches `schemas.py`'s broader lists closely (minus the later Nepal-specific additions of microbus/bus/jeep/scooter and dust).
- **`generate_nepal_data.py`** (the one that actually produced the committed `data/sample_data.csv`) uses a Nepal-specific vehicle list (car, microbus, bus, motorcycle, scooter, jeep, truck - no suv/van, since those aren't common vehicle categories on Nepal's roads) and doesn't generate snow as a weather condition at all (unsurprising for most of Nepal's climate).

In other words, `schemas.py`'s `Literal` types look like they were widened to be a superset covering both generators' vocabularies (plus the Nepal-only additions), but the model actually deployed today was trained only on `generate_nepal_data.py`'s narrower, Nepal-specific output - so the schema currently promises more input flexibility than the underlying model can actually accept.
